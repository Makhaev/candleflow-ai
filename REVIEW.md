# Ревью `reserve_material`

Разбор исходного фрагмента со страницы 5 PDF. Инструмент принимает словарь аргументов модели и напрямую увеличивает резерв в партиях. Ниже проблемы в порядке приоритета.

| Приоритет | Проблема и последствие | Исправление |
| --- | --- | --- |
| Критический | **SQL-инъекция.** `args['material']` подставляется прямо в строку `SELECT`. Параметры в отдельном `UPDATE` защищают только этот `UPDATE`. | Валидировать аргументы и передавать значения в запрос связанными параметрами. В CandleFlow запрос строится через SQLAlchemy, а аргументы модели описаны схемой Pydantic. |
| Критический | **Нет проверки роли и подтверждения.** Инструмент меняет остатки по команде модели. В сигнатуре отсутствует аутентифицированный пользователь. | Брать пользователя из серверной сессии. Проверять право планирования при подготовке предложения и повторно при подтверждении. Само предложение не меняет склад. |
| Критический | **Гонка между чтением и обновлением.** Два запроса могут одновременно прочитать одинаковый свободный остаток и оба увеличить резерв, рассчитанный по устаревшим данным. | Блокировать строки задания и партий через `SELECT FOR UPDATE` до расчёта. Обрабатывать коды материалов в одинаковом порядке, а партии по дате и ID. Ограничение БД служит дополнительной защитой от резерва сверх остатка. |
| Критический | **Нет явной транзакции на всю операцию.** При ошибке после нескольких обновлений часть резерва может сохраниться, если вызывающая сторона не обернула вызов в одну транзакцию. | Выполнять создание или планирование задания, обновление остатков, записи резервов, движения и аудит в одной транзакции. Неожиданная ошибка приводит к полному откату. |
| Высокий | **Неверный FIFO.** `ORDER BY id DESC` начинает с более поздних идентификаторов. Порядок создания партий может также отличаться от дат поступления. | Сортировать по `received_on ASC, id ASC`. ID задаёт устойчивый порядок при одинаковой дате. |
| Высокий | **Нет проверки статуса партии.** В выборку попадают партии на проверке и забракованные партии. | Фильтровать по `status = 'accepted'` до расчёта. PostgreSQL дополнительно запрещает ненулевой резерв для непринятой партии. |
| Высокий | **`float` и невалидные количества.** Двоичное округление делает вычитание и проверку `need == 0` ненадёжными. Сырой словарь допускает отсутствующие поля, отрицательное количество, NaN и бесконечность. При отрицательном `need` или уже повреждённом остатке `take` может стать отрицательным и уменьшить чужой резерв. | Проверять конечные количества, знак и допустимую точность на границе API. Хранить и вычислять количества как `Decimal` и PostgreSQL `NUMERIC`. Ограничение `0 ≤ reserved ≤ quantity ≤ received` защищает баланс партии. |
| Высокий | **Отсутствует связь с заданием.** Есть только суммарный резерв партии. По нему нельзя узнать, что выдать при запуске и чьи резервы снимать при отмене. | Хранить потребность отдельно и создавать запись `reservations` с ключом `(job_id, batch_id)` и внешними ключами на задание и партию. |
| Высокий | **Ложное сообщение об успехе.** Ответ повторяет запрошенное количество при частичном резерве, нулевом результате или неизвестном материале. | Возвращать потребность, фактический резерв и дефицит по компонентам. Запрещать запуск при ненулевом дефиците. |
| Высокий | **Нет идемпотентности.** Повторный вызов после таймаута может увеличить резерв ещё раз. | Для подтверждения использовать постоянный идентификатор предложения. Под блокировкой сохранить ID созданного задания и возвращать его при повторе. Для уже запланированного черновика повторный переход должен дать конфликт. |
| Высокий | **Нет аудита.** По обновлённому числу нельзя определить инициатора, прежнее значение и основание изменения. | В той же транзакции сохранять аудит с инициатором и снимками до и после, а также движение с ID задания и партии и изменением резерва. |
| Средний | **Небезопасное логирование.** `logger.info(..., args)` сохраняет сырой пользовательский текст и параметры модели. Это может раскрыть персональные данные или загрязнить журнал. | Логировать разрешённое имя операции, идентификатор вызова и результат без сырых аргументов. Хранить учётный аудит отдельно, с контролем доступа. |
| Средний | **Нет контракта для модели.** У инструмента только строка docstring: модель не знает имён и типов аргументов (`material` или `material_code`, единица `qty`) и угадывает их. Ответ — свободный текст, по которому модель не отличит успех от частичного резерва и не сможет честно сообщить дефицит. Отсутствующий ключ даёт `KeyError` и 500 вместо понятной ошибки. | Описывать аргументы JSON-схемой из той же Pydantic-модели, что валидирует вход. Возвращать структуру `{required, reserved, missing, unit}`, а ошибки домена — полем `error` с текстом для пользователя. В CandleFlow схема строится через `model_json_schema()`, ошибки `DomainError` и `ValidationError` возвращаются модели как результат инструмента. |
| Средний | **Единицы измерения.** Количество не связано с единицей материала: «500» может означать граммы при учёте в килограммах. | Принимать количество в единице карточки материала и возвращать единицу в ответе. Нормы рецепта задаются в той же единице. |
| Средний | **Лишняя работа.** `SELECT *` загружает все найденные партии, а цикл обновляет даже строки с нулевым `take`. | Использовать индекс под порядок FIFO и пропускать нулевые изменения. Измерять объём выборки и длительность блокировок на характерных данных. |

## Как резервирует CandleFlow

1. REST вызывает сервис планирования с аутентифицированным пользователем. Инструмент `create_and_plan_job` проверяет аргументы и право технолога или руководителя, затем сохраняет предложение. На подтверждении сервер проверяет владельца диалога, срок первого подтверждения и актуальную роль. После проверки оба пути используют один сервис, который управляет резервом. [REST API](candleflow/api.py) · [Инструмент и подтверждение](candleflow/assistant.py)
2. `plan_draft` блокирует черновик, затем обрабатывает материалы по коду. Для каждого материала `fifo` выбирает и блокирует принятые партии в порядке даты и ID. Под блокировкой сервис берёт минимум из оставшейся потребности и `quantity - reserved`. Положительный резерв отражается в партии, записи `reservations`, движении и аудите. Частичный резерв сохраняется как результат успешного планирования с дефицитом. Запуск такого задания отклоняется. [Учётный сервис](candleflow/inventory.py) · [Ограничения и индекс FIFO](candleflow/models.py)
3. Транзакцией управляет вызывающий API. Подтверждение блокирует сообщение и предложение, планирует задание и записывает его ID до общего commit. Повтор того же подтверждения возвращает существующее задание. Повтор планирования того же черновика отклоняется с конфликтом. Прямой `POST /api/jobs` создаёт новое задание на каждый запрос и не имеет отдельного ключа идемпотентности. [REST API](candleflow/api.py) · [API подтверждения](candleflow/chat_api.py)
4. Сырой словарь аргументов в журнал вызовов инструмента не пишется. В `tool_executions` сохраняются ID сообщения, порядковый номер, имя инструмента, модель, время и исход. SQLAlchemy скрывает параметры в диагностике. Учётный аудит сохраняет инициатора и снимки состояния и остаётся доступным через защищённые маршруты. [Журнал вызовов](candleflow/assistant.py) · [Настройка SQLAlchemy](candleflow/db.py)

Гарантии проверяются на PostgreSQL. Тесты покрывают FIFO и частичный резерв, два конкурентных планирования, запрет запуска с дефицитом, освобождение резерва, ограничения БД, отказ роли и два одновременных подтверждения одного предложения. [Учёт](tests/test_inventory.py) · [Ограничения БД](tests/test_normalized_schema.py) · [Роль ассистента](tests/test_assistant.py) · [Запуск, отмена и подтверждение](tests/test_acceptance_failures.py)
